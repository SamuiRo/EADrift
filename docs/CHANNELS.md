# Канали-джерела сигналів

Бот слухає кілька Telegram-каналів одночасно. Кожен сигнал записується з
**ім'ям свого каналу** в полі `source`, і вся статистика — реплей, звіти,
воронка відмов — рахується окремо по кожному каналу. Так видно якість кожного
джерела, а не змішане середнє.

## Як визначається джерело

| Як прийшов сигнал | `source` |
|---|---|
| З каналу, який бот слухає | ім'я каналу з `SIGNAL_CHANNELS`, напр. `ggshot` |
| Адмін переслав боту з каналу, що є в конфігу | ім'я цього каналу — так само, як автоматичний прийом |
| Адмін переслав з каналу, якого в конфігу немає | `forward:<назва_каналу>` — видно, звідки, і його легко додати |
| Пересилання з прихованим автором | `admin_forward` |
| Адмін набрав чи вставив текст вручну | `admin_message` |

Ім'я джерела видно в кожному повідомленні бота: `[ggshot]`.

## Конфігурація

```env
SIGNAL_CHANNELS=ggshot:-1001234567890,whales:@whales_signals:whales
```

Кожен запис — `ім'я:ідентифікатор[:парсер]`:

- **ім'я** — малі латинські літери, цифри, `_`, `-`, до 32 символів.
  **Не змінюйте ім'я каналу після запуску**: історія розділиться на дві частини.
- **ідентифікатор** — `-100…` або `@username`.
- **парсер** — формат сигналів цього каналу. За замовчуванням `ggshot`.

Акаунт Telegram, для якого створено сесію (`npm run auth`), мусить бути
підписаний на кожен канал. Якщо якийсь канал не вдалося підключити, решта
працюють, а в повідомленні `Bot started` буде `⚠️ Не підключено: ...` з причиною.

Старі змінні `TELEGRAM_SIGNAL_CHANNEL_ID` / `TELEGRAM_SIGNAL_CHANNEL_NAME`
працюють як один канал, якщо `SIGNAL_CHANNELS` порожній.

## Додати новий канал

1. **Надішліть 3–5 прикладів сигналів** цього каналу — повний текст, як він є,
   разом з емодзі. Бажано і LONG, і SHORT, і звіт про досягнення цілей, якщо
   канал такі публікує.
2. Якщо формат збігається з уже відомим — канал просто додається в
   `SIGNAL_CHANNELS` з цим парсером. Інакше пишеться новий парсер і тести на ці
   приклади.
3. Перевірка: перешліть боту приклад з каналу. Він має прийти з міткою
   `[ім'я_каналу]`, а не `[forward:...]`.
4. Оновлення сервера й рестарт. Нові сигнали йдуть у shadow.

Поки парсера немає, сигнали каналу можна пересилати боту вручну — вони
запишуться як `forward:<назва>`, тож нічого не загубиться.

## Якість каналу

```bash
npm run replay -- --detail                # розріз по каналах у кожній політиці
npm run replay -- --source whales         # лише один канал
npm run report -- --only sourceStats,evaluationFunnel,rejectionReasons
```

Що дивитися:

- **Частка відмов** і їх причини (`rejectionReasons`). Багато відмов
  «перевірка структури» — канал публікує неповні сигнали або парсер
  розходиться з форматом.
- **Середній R у реплеї** по поточній політиці — головний показник якості.
- **Розмір вибірки.** Канали з різною частотою сигналів набирають статистику
  з різною швидкістю; висновок по каналу — не раніше ~50 сигналів від нього.

Сигнали, що не пройшли перевірку структури, теж записуються з міткою каналу:
биті публікації — частина якості джерела.

## Калібрування

Параметри виходу (власний SL, сітка TP, поріг зваженого R:R) підбирались під
геометрію GGShøt: TP1 на ~1R від середини зони. В іншого каналу геометрія може
бути інша. Поки параметри спільні для всіх каналів; коли по новому каналу
набереться вибірка, реплей покаже, чи потрібна йому окрема конфігурація.
