# Збір і аналіз даних

Бот на сервері працює в `SHADOW`: кожен сигнал із каналу проходить усі фільтри,
рішення записується в базу, ордери не виставляються. Цей документ — про те,
як ці дані дістати й що з ними робити.

## Три способи отримати дані

### 1. Швидкий погляд — `/stats` у Telegram

Зведення по закритих угодах: win rate, середній R, досягнення TP, розріз по
джерелах. У SHADOW угод не відкривається, тому тут буде порожньо — для
shadow-даних потрібні способи 2 або 3.

### 2. Копія бази — `/export` у Telegram (основний спосіб)

Бот надсилає файл `eadrift-YYYY-MM-DDTHH-MM-SS.db` у чат адміністратора.
Копія знімається через `VACUUM INTO`, тобто цілісна навіть якщо саме в цей
момент записується новий сигнал. Бот при цьому не зупиняється.

Далі локально, у папці проєкту:

```bash
EADRIFT_DB_PATH=./eadrift-2026-10-15T12-00-00.db npm run replay -- --detail
EADRIFT_DB_PATH=./eadrift-2026-10-15T12-00-00.db npm run report
```

На Windows PowerShell:

```powershell
$env:EADRIFT_DB_PATH = ".\eadrift-2026-10-15T12-00-00.db"; npm run replay -- --detail
```

Файл містить сигнали, рішення й угоди. Ключів і сесій у ньому немає, але це
все одно ваша торгова історія — не публікуйте його.

### 3. Прямо на сервері по SSH

```bash
cd eadrift
npm run report -- --only evaluationFunnel,rejectionReasons
npm run replay -- --detail
```

Реплей тягне свічки з публічного API Binance, ключ для цього не потрібен.

## Що дивитися

| Питання | Звіт | На що звернути увагу |
|---|---|---|
| Скільки сигналів прийшло і що з ними стало | `evaluationFunnel` | співвідношення `SHADOW` до `REJECTED` |
| Чому відсіюються | `rejectionReasons` | якщо одна причина домінує — фільтр, можливо, надто жорсткий |
| Чи заробили б пропущені й прийняті | `npm run replay` | середній R по кожній політиці, частка плюсових |
| Чи варто щось міняти | `npm run replay` після зміни параметра в `riskEngine.js` | реплей імпортує живий код, тому зміна видна одразу |

`npm run replay` порівнює три політики: власний SL (поточна), власний SL без
переносу в BE, SL провайдера. Рядки, які наживо не пройшли б фільтр ширини SL,
позначені `⚠ поза maxDeltaPct` — їх не можна вважати досяжним результатом.

## Скільки даних достатньо

Для профілю цього провайдера (висока частота TP1, скромний R) потрібно
близько **80–90 сигналів**, щоб відрізнити реальну перевагу від випадковості.
При частоті ~1 сигнал на 3 дні це 7–9 місяців одного каналу.

Проміжні точки, на яких варто дивитися дані:

- **~20 сигналів** — перевірити, що нічого не зламано: причини відмов
  осмислені, немає систематичних помилок парсингу.
- **~50 сигналів** — перша змістовна оцінка політик, можна обговорювати
  параметри. Мінімальний поріг для розмови про live.
- **~85 сигналів** — висновок про наявність переваги з розумною впевненістю.

Реплей сам попереджає, коли вибірка менша за 30.

## Що надсилати на аналіз

Файл з `/export`. Цього достатньо: у ньому і сирий текст кожного сигналу, і ціна
на момент отримання, і повний знімок рішення. Свічки для реплею завантажуються
заново з Binance.

## Резервні копії

`/export` раз на тиждень і зберігання файлу у себе — найпростіший бекап.
Автоматичний варіант на сервері описаний у [DEPLOYMENT.md](./DEPLOYMENT.md#8-резервні-копії).
